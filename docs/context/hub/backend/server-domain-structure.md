# lib/server Domain Structure

Use this to decide which folder new server-side logic belongs in, and what it may import.

Reference: [src/hub/src/lib/server/](../../../../src/hub/src/lib/server/)

Notable:
* **Five domain folders, each with a narrow, one-directional set of allowed imports** — `storage/` (db + repositories, see [Database Handling](./database-handling.md)), `jobs/` (job-agnostic logic, with `recipeJobs/`/`trainingRunJobs/` subfolders for per-job-type creation and DSL-step reporting), `recipe/` (Recipe definition/validation/allowlist, no job or DB knowledge), `llm/` (client/config/prompts plus the two callers — `goalIngredients`, `nextStep` — that validate an LLM response), and `runner/` (auth, config, and the outer poll/report/upload handlers).
* **Allowed imports**: `jobs` → `recipe` + `llm` + `storage`; `llm` → `recipe`; `runner` → `jobs` + `recipe` + `storage`; `recipe` → nothing but core types (`$lib/types/*`) and storage's leaf value enums (e.g. `RecipeStatus`) — never a repository module. This keeps `recipe/` free of any DB dependency so it can never form a cycle with `storage/repositories/recipeRepository.ts`, which itself depends on `recipe/recipeDefinitionValidation.ts` to validate a definition before persisting it.
* **A route needing both a repository call and `recipe/`'s pure shaping stays a route concern, not a `recipe/` concern** — e.g. the recipes-listing endpoint fetches Recipes via `storage/repositories/recipeRepository.ts` itself, then calls `recipe/recipeActions.ts`'s `toRecipeSummaries(recipes)` (pure, no `db` parameter) to shape them for the wire. Don't reach for "recipe/ can just take `db` as a parameter" as a shortcut — that's exactly the shape that produced the storage↔recipe cycle this pattern exists to avoid.
* **`jobs/jobActions.ts`'s generic `reportJobStep` dispatches to `jobs/recipeJobs/reportDslStep.ts` / `jobs/trainingRunJobs/reportDslStep.ts` by job type, and those files import `jobs/jobActions.ts`'s `ReportStepBody`/`JobActionResult` types back** — a type-only circular import (erased at compile time, `import type` only), not a runtime cycle. Keep it type-only; a runtime import here would be a real cycle.
* **`runner/`'s outer handlers (`runnerPoll`, `reportJobStep`, `uploadJobStepArtifact`) do auth + Runner/Job lookup + ownership checks, then delegate into `jobs/` with an already-resolved `Job`/`Runner`** — `jobs/` never imports `runner/` (that would invert the allowed-imports direction), so a `jobs/` function always takes the resolved entities as parameters rather than doing its own auth/lookup.
