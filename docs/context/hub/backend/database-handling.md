# Database Handling

Reference: [src/hub/src/lib/server/storage/](../../../../src/hub/src/lib/server/storage/)

Notable:
* **`server/storage/db/` holds cross-cutting DB tooling, not per-table queries** — `connection.ts` (`openDb`/`resolveDatabasePath`/`requireDatabaseUrl`), `db.ts` (the app's `getDb()` singleton), `reset.ts`/`resetCli.ts` (the `db:reset` fast path), `recipeStatus.ts` (the `RecipeStatus` enum mirroring seeded system rows), and `dates.ts` (date translation) live under `src/hub/src/lib/server/storage/db/`.
* **`server/storage/repositories/` holds the per-table CRUD** — a sibling folder to `db/` under `storage/`, one light repository module per major domain entity (e.g. `customerRepository.ts`, `runnerRepository.ts`, `recipeRepository.ts`). Each repository function takes the `Database.Database` connection as its first argument (matching `reset.ts`'s `resetUserData(db, ...)`) rather than calling `getDb()` itself — callers (routes, `seed.ts`, `resetCli.ts`) get the connection from `getDb()`/`openDb()` once and pass it down. No generic/shared query builder, no ORM.
* **Migrations via dbmate** — `npm run db:migrate:up` / `db:migrate:down` / `db:migrate:new -- <name>` wrap the `dbmate` CLI (npm package, run through nx targets on the hub project) against `db/migrations/*.sql` files, each with `-- migrate:up`/`-- migrate:down` sections. `db/schema.sql` is dbmate's auto-dumped schema snapshot — don't hand-edit it.
* **`HUB_DATABASE_URL` is required, not defaulted** — `connection.ts`'s `requireDatabaseUrl()` throws if it's unset rather than falling back to a default path, per this repo's "let it crash on missing config" rule. Copy `src/hub/.env.example` to `src/hub/.env` for local dev (gitignored); Playwright's `webServer` config overrides it to `sqlite:.data/hub.e2e.db` so e2e runs never touch the dev database.
* **`getDb()` reads env via `$env/dynamic/private`**, so it only works inside SvelteKit's server module graph. Anything run as a standalone script (like `resetCli.ts`) reads `process.env.HUB_DATABASE_URL` directly instead, and uses explicit `.ts` import extensions since plain `node` execution bypasses Vite's resolver.
* **`db:reset` only clears user-defined tables** — `reset.ts`'s `resetUserData()` deletes rows from `recipe`, `runner`, `customer_application_xref`, `application`, and `customer`, skipping tables that don't exist yet and never touching `recipe_status` (system data, seeded by the migration itself with explicit ids) or dbmate's own `schema_migrations`. It's for fast reuse between test runs — it doesn't re-run migrations.
* **Dates are translated at the DB boundary, nowhere else** — SQLite has no timestamp type, so date columns (`last_heartbeat_on`, `created_at`, `published_at`, ...) store ISO-8601 text. Use `dates.ts`'s `toDbDate`/`fromDbDate` right at the SQL call in each repository — both have a `Date | null` overload for nullable date columns, so repositories never reinvent null-handling. Code outside `lib/server/storage/db` should only ever handle real `Date` objects (or `null`), never a raw date string, and should never need to call `new Date()` itself to parse one.
* **Foreign keys are enforced** — `connection.ts`'s `openDb()` sets `PRAGMA foreign_keys = ON` on every connection, since SQLite otherwise ignores `REFERENCES` constraints. A bad reference throws at the `INSERT`/`UPDATE`, it doesn't silently succeed.
* **Unit tests never touch a real database; integration tests always do** — anything that needs a real schema to verify (repositories, `reset.ts`, `openDb()`'s file/FK behavior) is an `*.integration.test.ts` file, run by `npm run guard:hub:test-integration` (`vite.integration.config.ts`, node environment). Each integration test file's `useIntegrationTestDb()` (in `storage/db/_test/integrationTestDb.ts`) migrates one real scratch sqlite file with the real `dbmate` CLI once (`beforeAll`) and calls the real `resetUserData()` before every test (`beforeEach`) — never a hand-duplicated schema. Plain `*.test.ts` files (`vite.config.ts`, jsdom environment, `npm run guard:hub:test`) stay pure/fast: mocked or pure-function tests only (e.g. `dates.test.ts`, `db.test.ts`'s mocked `getDb()`).
